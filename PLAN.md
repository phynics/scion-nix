# Scion Nix bootstrap plan

## Goal and initial scope

Publish a flake that installs a ready-to-use `scion` CLI and web dashboard on `x86_64-linux`, `aarch64-linux`, `x86_64-darwin`, and `aarch64-darwin`. Provide NixOS and nix-darwin modules for the CLI and native Scion services, each with an explicit service account. Publish the Linux agent images needed for ordinary agents, so a user downloads binaries and images instead of building either on their machine. A native Hub-only deployment needs neither images nor a container engine. The first supported deployments are a workstation on both operating systems and a single-node NixOS Hub and Broker. HA, Kubernetes, cloud-specific images, and optional plugins are later work.

The flake is the versioned deployment interface. CI builds the native Nix packages and Linux OCI images from one pinned Scion revision, tests them, and publishes them. A public Nix binary cache makes normal flake installation substitute built outputs. An OCI registry serves images to Podman or Docker on both host platforms. Nix may still build from source when a cache entry is absent; document that behavior and make release availability a gate before announcing a version.

## Facts that drive the design

- Scion's host CLI starts agents directly in Local mode. Workstation mode starts the Hub, Runtime Broker, and embedded web dashboard in a single process. Agents run in **Linux** containers, including on macOS. The Hub image is not required to run a native workstation or NixOS service.
- The Hub and Runtime Broker are native processes from the host `scion` binary: the Hub can run without Docker or Podman, and a standalone Broker can start natively. A Broker that executes ordinary harness agents still needs a supported container runtime and the agent OCI images. Hub-managed cloud agents bypass the Broker and local containers, but currently target repo-less work. Do not describe native services as native execution of containerized agents.
- Upstream `go.mod` on `main` specifies Go `1.26.1`; this must be checked again at the chosen pinned revision. The frontend is built with Node and `web/package-lock.json`. `web/embed.go` embeds `web/dist/client` in the host Go binary. A Go-only build leaves the dashboard unusable. Upstream `make all` builds the web client first.
- Upstream image tooling has a dependency chain: `core-base` to `scion-base` to the harness images and `scion-hub`. The harness image set is discovered from `harnesses/*/Dockerfile`, so do not freeze a guessed list into the release workflow. The normal `all` build supports `linux/amd64` and `linux/arm64`; the `thick` and `omni` targets are amd64-only and out of initial scope.
- `scion-base` contains a Linux `scion` binary, `sciontool`, an entrypoint, and the required agent user setup. Replacing it with an image that contains only the host binary would break agent startup. The upstream Dockerfile builds a `no_embed_web` CLI for the agent image. Preserve and test the full entrypoint contract.
- `image_registry` rewrites standard `scion-*` image references, but an explicit agent or template image overrides it. Image publishing, default tags, and the config seen by Scion must agree. OCI images are Linux artifacts; a Darwin host pulls the matching Linux architecture through its container runtime.
- The upstream installation guide requires Git >= 2.47 for its worktree behavior. Podman or Docker is needed to run agents; on macOS Podman needs a running `podman machine`. Apple Container is experimental and its Hub DNS setup may require a privileged boot-time rule. Start with Podman as the supported macOS path.
- As of the research date, upstream `LATEST.json` has no stable channel. Preview and nightly tags exist, but the advertised preview tag and GitHub's newest preview release need not match. Pin an **exact commit and checksum**, record its version separately, and test that pair; never follow `main`, `latest`, or a moving nightly tag during evaluation.

Source material: [overview](https://googlecloudplatform.github.io/scion/overview/), [installation](https://googlecloudplatform.github.io/scion/getting-started/install/), [custom images](https://googlecloudplatform.github.io/scion/local/custom-images/), [workstation](https://googlecloudplatform.github.io/scion/workstation/workstation-server/), [Runtime Broker](https://googlecloudplatform.github.io/scion/hosted/ha/runtime-broker/), [managed agents](https://googlecloudplatform.github.io/scion/hosted/single-node/managed-agents/), [server configuration](https://googlecloudplatform.github.io/scion/reference/server-config/), [image build targets](https://github.com/GoogleCloudPlatform/scion/blob/main/image-build/scripts/lib/targets.sh), [Makefile](https://github.com/GoogleCloudPlatform/scion/blob/main/Makefile), and [Go embed declaration](https://github.com/GoogleCloudPlatform/scion/blob/main/web/embed.go). These are current upstream references, not promises about a future pin.

## Intended user interface

Expose `packages.<system>.google-scion` and `packages.<system>.default`, `nixosModules.default`, and `darwinModules.default`. Expose `checks.<system>` for the builds and evaluations. Linux-only image archive outputs may be named `packages.<linux-system>.scion-<harness>-image` after their format and runtime import behavior have been verified. Keep the native package and image release version together in a small checked-in release manifest with the Scion commit, source hash, image names, per-platform immutable digests, and publication status. Stage the manifest update after CI has published and inspected the images; it cannot contain final digests before that build.

Separate installation from long-running processes. `programs.google-scion` owns interactive CLI installation, default runtime, and image registry. Every service uses `programs.google-scion.package` by default, even if the interactive CLI installation is disabled; add a per-service package override only for a proven need. All three services run the native host binary under the OS service manager. `services.scion.workstation` owns the combined Hub, Broker, and web process. `services.scion.hub` and `services.scion.broker` own separate processes for a hosted deployment. Never enable the combined workstation and either standalone service against the same ports and state directory. The target interface is:

```nix
programs.google-scion = {
  enable = true;
  package = inputs.scion-nix.packages.${pkgs.system}.google-scion;
  runtime = "podman"; # or "docker"; explicit, no runtime auto-detection
  imageRegistry = "ghcr.io/OWNER";
};

services.scion.workstation = {
  enable = true; # optional, off by default
  user = "agents"; # existing account; Scion and rootless Podman run in its context
  listenAddress = "127.0.0.1";
  port = 8080;
  environmentFile = null; # absolute runtime path, never file contents
};

# Later, on NixOS, when running components separately:
services.scion.hub = {
  enable = true;
  user = "agents";
  stateDirectory = "scion-hub";
  environmentFile = config.sops.secrets.scion-hub-env.path;
};
services.scion.broker = {
  enable = true;
  user = "agents";
  runtime = "podman";
  environmentFile = config.sops.secrets.scion-broker-env.path;
};
```

This is a **target interface**, not implemented Nix syntax. The workstation example assumes an NixOS account named `agents`; on macOS, set `user` to the login account that owns the Podman machine. First deliver `programs.google-scion` and `services.scion.workstation`; add separate Hub and Broker services with the single-node deployment. The package module installs the CLI, a sufficiently new Git, and shell completions if their generation is safe at build time. Service modules start Scion in the foreground with the selected `programs.google-scion.package`; the OS service manager owns the process. A plain flake package install remains valid without any service module. Each service has its own required `user` option; it names an existing OS account. The modules never create accounts implicitly. Check option types and conflicting service combinations during evaluation, but do not reject a user merely because it is absent from NixOS `users.users`: NSS and other account managers can supply it. Check account existence and file and runtime access when the service starts.

Make the container dependency conditional on **agent execution**, not on starting a Hub. A native Hub-only configuration needs no container engine or image download. A standalone Broker or workstation that launches regular harness agents needs Podman, Docker, or another supported runtime and the published images. If a Hub uses only the managed-agents profile, it can operate without a local Broker or images; document its cloud credentials and workspace limitations separately. Set Scion's scheduled update policy to `disabled` for Nix-managed services. Upstream says manual maintenance actions can still run with that setting, so test and document how to prevent or reject binary and web rebuild actions rather than assuming this setting blocks them.

### Traditional and sops-nix configuration

Keep the modules independent of sops-nix. The traditional path can declare nonsecret Scion settings and pass an existing service-readable environment file through `services.scion.<component>.environmentFile`. The module must not place API tokens, OAuth secrets, or session secrets in Nix option string values, store paths, command arguments, or generated world-readable settings. Document provider credentials for a user-run CLI separately from server credentials; an OS service cannot assume it inherits an interactive shell's environment.

For sops-nix, accept a decrypted **path** from `config.sops.secrets.<name>.path` through the same `environmentFile` option. The secret file must use the environment-file syntax expected by the chosen service manager and contain, for example, `SESSION_SECRET=...`. Configure file ownership and permissions for each service's `user`; a file readable only by `agents` cannot serve a component configured to run as another user. On NixOS, order the systemd service after sops-nix secret installation, load it through systemd `EnvironmentFile`, and verify startup after activation and after a reboot. On nix-darwin, test launchd's actual environment-file support before defining the equivalent: if launchd cannot safely read such a file, use a small runtime wrapper that reads the file at service start, exports variables, and `exec`s Scion. The wrapper's script text may be in the store, but decrypted values and their paths' contents must never be copied there. Do not add sops-nix as a required flake input.

Scion's `~/.scion/settings.yaml` is mutable application state under the **selected service user's home**, which can differ from the interactive CLI user's home. Keep schema-validated, nonsecret settings separate from secrets. Workstation and Broker use the selected user's real home and rootless runtime context; do not imply that creating a separate directory redirects Scion's settings. The Hub uses its account's home for settings and systemd `StateDirectory` for explicitly configured SQLite and storage paths. Do not run `scion init --machine` on each Nix evaluation or overwrite an existing user's settings during activation. For first use, document a one-time initialization under the selected user or provide an idempotent initializer that preserves existing files. `image_registry` changes the registry prefix but preserves the image tag; it does **not** pin the release. For the first release, use a versioned registry tag, and validate how explicit harness image overrides reach both the service account and an interactive CLI user. Preserve user template overrides; document that a custom image remains the user's responsibility. Do not claim that `imageRegistry` alone locks the images.

## Build and release architecture

1. **Pin inputs.** Add `flake.nix`, `flake.lock`, and a documented upstream pin. Pin nixpkgs to a revision with a suitable Go toolchain and Node toolchain. Fetch Scion with an immutable revision and fixed-output hash. Track package version and commit independently; upstream `hack/version.sh` uses Git metadata and build time, which a source archive does not provide automatically. Inject deterministic `Version`, `Commit`, and `BuildTime` values with upstream-compatible `-ldflags` and test `scion version`.
2. **Build the native package.** Use Nix's Go builder (`buildGoModule`) with a fixed vendor hash and no network in the build. Build the locked frontend first using a Nix npm builder with a fixed npm dependency hash, then copy `dist/client` into the Go source tree before compilation. Preserve required `web` assets and source files; avoid `no_embed_web` for the host binary. Set the appropriate SQLite and CGO flags based on a build test on both operating systems. Check that the binary starts a server and serves actual client assets, not merely a blank index. Do not use upstream `make web`'s mutable `npm install` in the Nix build.
3. **Build OCI images in CI from the same upstream revision.** Initially use upstream's `image-build/scripts/build-images.sh --target all --platform all --registry ghcr.io/OWNER --tag <release-id> --push` with Buildx. This retains upstream's entrypoint, filesystem, and harness installers instead of inventing an incomplete Nix image. Pin and record external base image and harness dependency versions or digests as necessary for repeatable releases; upstream Dockerfiles and third-party installers must be audited for moving inputs. Publish a source revision tag and immutable digest for each image and architecture. Confirm that tag resolution yields the expected manifest and architecture before promotion. The registry namespace and visibility must be established before the first release.
4. **Make the image artifacts available through the flake.** For each published Linux architecture, add a fixed-output image archive derivation using an OCI pull mechanism such as `dockerTools.pullImage`, pinned to the **platform-specific** digest and Nix output hash. Test loading its result into both Docker and Podman before advertising this output. Keep `scion-hub` optional for users running a native Hub. Regular Darwin users pull published images from GHCR through Podman; do not pretend a Linux image is a Darwin binary. If the Nix image archive approach cannot preserve the upstream runtime contract, keep the verified registry pull as the installation path and make that limitation explicit until an archive passes tests.
5. **Publish native substitutes in two stages.** First, CI builds and tests packages for all four systems from a reviewed upstream pin; a release job builds and pushes the Linux images from that same pin. Inspect their manifest lists and record per-platform digests in a reviewed manifest update. Second, build and test the final flake revision against that manifest and publish its native packages and image archives to a public signed Nix cache. Release only if every advertised system substitutes from the cache and every pinned image digest is available. Linux runners build Linux packages; macOS runners build Darwin packages natively unless a proven builder can substitute them. PRs evaluate and build without publication credentials. Grant registry write credentials only to publication jobs. Document cache setup and its signing key, plus a `nix build` fallback for cache misses.

The image build is a CI release job invoked by a flake `app` or repository script, not a side effect of `nix flake check` or Nix evaluation. A user can obtain the pinned images through the registry without any local compilation. Nix image archive outputs provide a separate, hash-checked offline import path once verified. Do not call an OCI registry tag a Nix store artifact or promise that installing the host package automatically starts a container engine.

## OS integration

- **NixOS:** support rootless Podman as the default Broker and workstation runtime; permit a configured Docker daemon as an explicit alternative. Install the native binary and Git. Use a systemd **system** unit with `User=` for a selected account only after testing its rootless runtime directory, socket, user namespace setup, and login-independent operation; switch to a user unit under that account if the system unit fails that test. Do not silently run a broker as root. The workstation and Broker use the selected account's home for Scion state and Podman. For a Hub, use systemd `StateDirectory` with a relative name, so systemd creates and owns `/var/lib/<name>`; set SQLite and storage paths explicitly to that directory. Use `scion server start --foreground`, restart policy, and a loopback listener for a workstation. Run a separate Hub under its configured account with SQLite backup, authentication, and explicit network exposure. Verify permissions independently when Hub and Broker users differ. Check that agents can reach the Hub through the selected container network.
- **nix-darwin:** install the CLI and Git, and use an existing Podman machine owned by the workstation account. Run a launchd user agent only when `services.scion.workstation.user` is the login account that owns it. A launchd user agent cannot switch users. Reject a different `user` with a clear assertion in the initial version; add support for a system LaunchDaemon with `UserName` only after its home, Podman machine lifecycle, and secret loading are tested. Start Scion in the foreground. Do not silently enable Apple Container: its system service and reboot-sensitive DNS/PF rule need a separate, privileged, tested opt-in. An installed CLI does not imply a running Podman machine.
- **Both:** avoid placing `~/.scion`, image layers, SQLite files, or credentials in the Nix store. Match the published `imageRegistry` and image tags expected by the pinned CLI. For a Broker or workstation that executes ordinary agents, pre-pull the chosen harness images when a runtime is available, or have onboarding pull them. Do not require images or a container engine for a Hub-only deployment. Give useful failure messages for an absent runtime when agent execution is requested, unavailable image architecture, missing Git version, and missing registry credentials.

## Delivery order and evidence

1. **Repository baseline:** license and README, source and nixpkgs pins, flake output names, and a release manifest schema. Verify `nix flake show` and evaluation on all four systems. Record which upstream tag or commit, toolchain, and image registry will form the first release.
2. **Native package:** frontend and Go builds, metadata, and completions. Build on all four target systems; inspect `scion version`, run the server, and fetch its web page plus a real static asset. A missing frontend fails the check.
3. **Runtime images:** build and publish the complete agent image set for amd64 and arm64 from the same revision. Inspect manifests and digests. On Linux, launch one representative image and exercise `sciontool` entrypoint and non-root agent behavior; on Apple Silicon, pull and run an arm64 image under Podman machine. Confirm a `scion start` and attach or logs workflow end to end.
4. **Modules:** evaluate NixOS and nix-darwin examples. Test installation without services, then a foreground workstation service under a named account with Podman. Check the actual process UID, selected Scion binary, home and state ownership, Podman access after reboot, loopback binding, web assets, restart behavior, no duplicate daemon, persistence across upgrades, and no write to an existing `settings.yaml`. Test both a manually supplied `environmentFile` and a sops-nix-provided secret path under that account; inspect the evaluated store closure to ensure secret contents are absent. Test evaluation failures for conflicting service combinations. Test a missing account, unreadable secret file, and inaccessible runtime at service startup; include an account supplied outside `users.users`.
5. **Single-node hosted NixOS:** add separate `services.scion.hub` and `services.scion.broker` modules and a deployment example. Verify a Hub-only service starts without a container engine, then test agent execution with an enabled Broker and published images. Check each process runs under its configured account, `/healthz` and `/readyz`, authentication, SQLite backup and restore, and upgrade rollback. Test both a shared service account and distinct Hub and Broker accounts. Verify scheduled updates are disabled and determine the behavior of manual rebuild controls. Keep HA out of the initial release.
6. **Cache and release automation:** perform a clean-machine install from the final manifest revision with the configured public cache and no compiler on the user's path. Verify the host binary is substituted and agent images are pulled, not locally built. Add an upgrade and rollback test that pins old and new flake revisions and checks the resolved image digests. Publish only after these checks pass.

## Fixed choices and release prerequisites

- Start from the exact commit behind upstream's `v0.3.0-preview.3` tag as the candidate first pin, not a moving branch or tag lookup. Verify its source checksum, Go directive, web lockfile, and actual version output before recording it in the flake. If it fails those checks, pick another exact commit and record why. No stable upstream channel is available yet.
- Use Podman on macOS and rootless Podman on NixOS for the first workstation test. Docker is an explicit NixOS alternative. Require a pre-existing service account. On macOS v1, it must be the login account that owns the Podman machine. On NixOS, prove that the named account can run rootless Podman without an interactive login before shipping an unattended Broker.
- Publish all standard harness images discovered at the pinned revision, plus `scion-hub` as an optional artifact because upstream's `all` target builds it. Do not download `scion-hub` for native services. Do not advertise `thick` or `omni` on arm64.
- Do not manage or overwrite an existing `~/.scion/settings.yaml`. Use service flags and environment settings for process-owned configuration where upstream supports them, and document one-time user setup. A pinning integration test must prove how selected harness images get the immutable release tag or digest for both service and interactive CLI users. Failure blocks the claim that installing the flake pins agent images.
- Use GHCR under the eventual repository owner's namespace and a public signed Nix cache, with Cachix as the initial cache provider. The owner must choose and provision the actual GHCR namespace, cache name, signing key, and macOS and Linux CI runners before publication. Until that is done, development builds can run, but the no-local-compilation release criterion cannot pass.

## Ready-to-release criteria

A release is ready when the same pinned Scion commit produces working native packages on all four systems and published standard agent images on both Linux architectures. The host binary serves its embedded web assets. A Hub-only NixOS service runs without Podman or images. A workstation on each OS and a NixOS Broker can start and interact with an agent using a published image. Each service runs as its configured account with persistent, writable state and runtime access. Manual and sops-nix secret-file paths work without storing secret contents in a Nix output. A clean machine substitutes the native package from the public cache, pulls the expected image digest, and starts no local compilation. The release manifest identifies those exact artifacts and an older flake revision remains usable for rollback.

## Why this architecture

Two approaches were considered. Rebuilding Scion's full Debian-based agent image hierarchy as Nix `dockerTools` layers could make image creation one pure Nix build, but the upstream entrypoint, UID mapping, shell toolchain, and third-party harness installations make that a separate port with a large compatibility burden. Using the existing upstream Dockerfiles for image creation, while the flake packages the native binary and pins published image archives, gets a working cross-platform release sooner. Revisit Nix-native image construction only after the first release's agent startup and upgrade tests are automated.
